This is the first review candidate for structured RGB-D observation adapters for Jev. It implements general_pickup, fold_clothes (including randomized suffix/prefix variants), press_by_number, match_and_pick_from_conveyor, stack_bowls (including randomized variants), and optional stack_blocks. It has not been imported, executed, or evaluated in a simulator in this worker session: the available tools provide allowed-source reads and generated-file writes only. Native success is unknown. Exceeding 20% full-task success in each family is an experimental target, not an outcome promised by this implementation. This candidate is not yet frozen for the judgment collection phase.

Files are controller.py, visual_evidence.py, and __init__.py. They form an importable package; alternatively put this directory on the import path and import Controller from controller. There is no installation step, file access in policy execution, environment-variable access, simulator RPC, API transport implementation, reward access, task implementation import, checkpoint download, or runtime file writing. The runner owns callbacks, execution, artifact persistence, evaluator-only native outcomes, and hard resource enforcement. No permanent test scripts were created.

**Boundary and source review.** The worker read only the allowed rgbd_bridge.py, rgbd_memory.py, realman_jev/robodojo_rgb.py and robot kinematics.py interface files. No task implementation, reward, layout, asset, audit, credential, or scripted task solution file was read. RGBEvidence was reviewed but is not imported: its configuration requires detector/SAM cache/model settings that are absent from the supplied settings interface, its IDs use same-camera IoU, and it cannot read printed button numbers or garment landmarks. A restricted RGB callback supplies essential visible semantics in this baseline. Coordinates and target geometry are computed deterministically from depth and calibration. The prior 20/20 oracle result is not visual evidence; 37 correct required-motion axes and two false movements on true-hold axes from 13 correlated visual steps do not calibrate confidence. No historical direction score enters online state, gain selection, or a confidence threshold.

**Runtime contract.** Controller(task, settings).step(observation, ask_jev, perceive) returns the specified stage/arms/ticks/stop/reason/debug dictionary. Instantiate a new controller for each episode. Recognized task names equal a family name, begin with family + underscore, or end with underscore + family. All five required families plus stack_blocks are implemented. Images are uint8 HWC RGB, depth is optical-Z in meters, and camera calibration must describe that image's acquisition time. Robot arm order is left, right; states[6] and states[13] are gripper openings. All commands use nominal grasp-point DELTAS, not link6 targets or absolute Cartesian positions. Every target quaternion is a normalized wxyz world-frame quaternion. Inactive arms are omitted. Returned ticks are between 1 and 15 and bounded by remaining_steps when it is positive. For stop=True the runner must not execute another action, even though the interface still requires ticks>=1.

The helper uses exactly:

    p_optical = depth_Z * inverse(K) @ [pixel_x, pixel_y, 1]
    p_relative = camera_to_world_opengl @ [p_optical * [1,-1,-1], 1] - env_origin
    nominal_grasp = observed_link6 + R(observed_wxyz) @ [gripper_bias,0,0]

The array implementation uses equivalent row-vector multiplication. There are no absolute layout coordinates. Constants such as a 55 mm pregrasp clearance, 75 mm lift, 6 mm press stroke, and 55 mm arm-point separation guard are explicitly external controller offsets/limits, not scene measurements or asset sizes. Visible bounds are depth quantiles, not a claim about unobserved object dimensions.

**Restricted perception contract.** The exact prompt is the PROMPT string in visual_evidence.py. It forbids actions, task roles, directions, stages, goals, waypoints, solutions, object XYZ, and hidden surfaces. Its exact parsed response fields are:

    {"views": {"<actual camera name>": {"objects": [
      {"category": "object|bowl|container|button|cloth|support|conveyor|reference",
       "label": "visible noun", "appearance": "visible color/shape/pattern",
       "text": "visible printed text or empty string", "confidence": 0.8,
       "polygon_uv01": [[0.1,0.1],[0.2,0.1],[0.2,0.2]],
       "keypoints": {"<visible landmark name>": [0.15,0.15]}}
    ]}}}

Confidence is only a subjective visibility rating, with a permissive >=0.5 record filter; it is not a probability of correct grasp or correct task interpretation. Category/text/outline/keypoints are perceptual outputs, not policy decisions. The controller derives task roles itself from public instruction and these measurements. The callback receives a reduced dictionary containing instruction and cameras[name].rgb only. It does not receive depth, calibration, robot state, controller stages, goals, or execution history. This reduced callback payload must be supported by the runner's perception transport; if the transport assumes every full observation field exists, adapt transport packaging without exposing policy targets to vision. The returned JSON is parsed through a field allowlist and bounded to 24 records and 96 outline vertices per camera. Extra fields cannot become actions.

Semantic calls occur initially, every five controller observations by default, after loss of optical-flow coverage, on bounded recovery, and during verification. Between calls, forward/backward Lucas-Kanade flow and a RANSAC partial affine fit track visible regions; coordinates are always relifted from the current depth image. Cloth keypoints have their own local flow measurement and are not propagated using the rigid outline transform. The vision module holds only one preceding RGB grayscale image per camera, current semantic regions, and a short track map. Perception callback count/seconds and Jev count/seconds are separate in debug. Token/billing accounting is explicitly delegated to callback/runner logs; the controller does not invent token cost. Local OpenCV work is not included in the callback timing field.

**Visual estimates and identity.** Polygon interiors are eroded before lifting. Invalid depth is rejected. A quantile trim, visible surface median, PCA normal, visible bounds and upper-surface samples provide geometry. Button polygons must exclude the surrounding panel. Bowl rim candidates are actual high visible depth samples at four horizontal extrema; the chosen rim side is held consistent. Garment half-fold corners are visible outline vertices nearest a fitted rectangle's corners, inset by three pixels, then locally tracked. They are seeded only at initialization and are never silently recreated after a tracking loss.

Cross-camera fusion requires compatible category, exact printed text, overlapping noun tokens, chromaticity, less than 25 mm metric separation, and distinct camera membership. Cloth landmark names remain tied to one measurement camera because image-relative left/right could invert between views. Frame-to-frame identity requires compatible semantics/color and less than 100 mm displacement. A nearest-vs-second-nearest margin above 18 mm and one-to-one assignment are required. Ambiguous matches get new IDs; an active plan is not silently reassigned. IoU is not an identity key. These gates are heuristic and deliberately stop on unresolved ambiguity; they cannot guarantee identity through crossings, occlusion or deformation.

An absent object remains in memory for at most three controller observations by default (not three physics ticks). Its observed flag becomes false, age increases, source explicitly says memory, and uncertainty increases by 6 mm per missed controller observation when used in a target. No predicted carried object is inserted into the observation map. Conveyor lead and carried offsets are separately labeled predictions/approximations. Contact, initial grasp baseline, destination placement geometry, and all verifications require current measurements. During a cloth transport, a missing destination landmark may retain its last measured goal until the phase limit of 32 observations; it is labeled a frozen visual target and must be reacquired before lowering. This frozen goal is not a claimed live cloth landmark. The button precontact surface is intentionally fixed during contact/stroke/retraction to prevent the target receding as the button moves. Both forms of phase goal memory expire with the bounded phase/episode; they are distinct from the three-observation live object memory.

The reported uncertainty is a 3 mm minimum plus a heuristic visible-plane residual contribution, capped at 35 mm. It is neither a calibrated confidence interval nor a bound on segmentation or systematic calibration error. Cross-camera disagreement increases it. Targets above 25 mm uncertainty and contact/lowering targets above 12 mm uncertainty are rejected. The current geometry estimator can underestimate systematic errors; this is a major untested assumption.

**Two selectable Jev schemas with identical permissions.** settings['schema_variant'] selects numeric or relational. Both receive identical public language, task variant, explicit subtask/stage, visual IDs, robot feedback, visibility flags, uncertainty, bounded history, available execution feedback, and external constraints. Neither receives images, reward, evaluator result, or simulator information. previous_execution is filtered to explicit mechanical fields: ik_converged, position_error_m, rotation_error_rad, joint_limit_hit, collision, executed_ticks, tracking_error_m, command_clipped and per-arm dictionaries. Unknown fields and free-form messages are dropped. An externally supplied success/score/reward field is never consulted or forwarded.

The numeric representation provides current_grasp_xyz_m, target_xyz_m, target_minus_grasp_m, distance_m, uncertainty_m, and measured surface geometry. The relational representation provides entities with the same measured coordinates/bounds and per-arm/per-axis relationships: target_above_axis_coordinate, target_below_axis_coordinate or overlaps_dead_zone, a signed separation interval [error-uncertainty,error+uncertainty], current/target coordinate, and distance to the dead zone. Those intervals are descriptive uncertainty bands, not calibrated intervals. Representation differs; observation permission does not. Relational predicates do not choose the executable sign. A deliberately wrong Jev response still produces that wrong sign unless a disclosed guard suppresses the entire command.

Questions are named left_x/left_y/left_z and/or right_x/right_y/right_z. Each has type='choice', instructions, and criteria mapping negative/hold/positive to their meanings in the world coordinate frame. There are no hidden stage, arm, gripper or rotation questions. Those choices belong entirely to the external scaffold and are labeled as such. The callback's native raw response is logged, including model, choices, confidence and probabilities; only its explicit choice is used for direction. Reported Jev confidence/probabilities do not control gain.

**Translation and external action rules.** For each target error coordinate e and heuristic uncertainty u:

    dead_zone = max(position_tolerance_m, u)
    amplitude = min(0.025, 0.70 * abs(e))
    amplitude = 0 inside the dead zone
    scale all three amplitudes by min(1, max_step_m / norm(amplitudes))
    delta = amplitude * Jev_sign   # negative=-1, hold=0, positive=+1

max_step_m is capped at 40 mm. Press-contact and press-stroke use min(position_tolerance_m,2 mm) before taking max with uncertainty. All amplitudes are nonnegative. Jev hold is exactly zero. Signs are never flipped, replaced with error signs, or silently corrected. The per-axis mask, amplitude, common scale, raw signs, raw response and executed deltas are logged. Axis convergence means every coordinate is inside the disclosed dead zone, so Euclidean residual may be up to sqrt(3) times that zone. A masked false movement must still count as a false raw direction judgment; separately report that execution suppressed it. Four consecutive all-hold translations outside convergence stop the episode. There is no fallback that fabricates translation when Jev holds.

Orientation aligns tool local +X toward a measured surface (downward for tabletop grasps); local Y uses a visible principal/landmark axis. Quaternion increments are capped at 0.20 rad. Pregrasp orientation actions hold the nominal grasp point with zero translation, explicitly without a Jev call. Gripper-only close/open and evidence-wait steps similarly have zero translation and an external-rule log. The runner must implement nominal-grasp-point-preserving rotation using the supplied bias when converting to link6 targets. This is distinct from holding link6 fixed.

A simple observed point guard stops the entire proposed action if the swept nominal grasp points would approach within 55 mm while closing distance, or a nonpress endpoint would cross a measured support plane (1 mm allowance, 3 mm for cloth). It never substitutes a new direction. This guard is not robot-body, finger, object or swept-volume collision checking. Suppressed proposals remain in debug for attribution. The runner's bounded IK and actual robot feedback remain necessary.

**Implemented family scaffolds.**

| Family | Public/visible selection | External phases and progress evidence |
| --- | --- | --- |
| general_pickup | Unique noun/color/text match, or one visible candidate; a receptacle is selected only when public placement language identifies one | approach 55 mm above grasp, contact, close, lift 75 mm, verify twice. If a destination exists: transport, lower, release, retreat, verify twice. Pure pickup stops holding the visibly lifted item; only evaluator determines task success. |
| press_by_number | Explicit public digit/number-word sequence, or an explicit ascending/descending/numerical-order rule applied to unique visible button OCR | approach 30 mm along measured face normal, contact 1 mm outside original face, bounded 6 mm inward stroke, verify visible button motion, retract 35 mm, repeat public sequence. No hidden order or activation flag. |
| match_and_pick_from_conveyor | Public description, or unique visible reference image/pattern descriptor matched to a visible item | Same pickup scaffold, but requires two fresh centroid measurements, estimates motion per native step, uses a 2/4-step lead capped at 25 mm, and executes two-tick translations. No static-target convergence assumption. |
| stack_bowls | Separate visible bowl instances; explicit public bottom-object language if present, otherwise largest visible footprint is the external base heuristic | Pick a visible rim sample, lift and verify; align visible source lower envelope over observed destination rim/top using a measured carry offset, release, retreat, verify. The newly placed item becomes the next measured destination. Every stack member is protected from reselection. |
| fold_clothes | One language-grounded garment; sleeve landmarks when sleeves are explicitly requested, otherwise hem-to-shoulder landmarks, otherwise tracked outline half-fold corners | One arm for a sleeve or two arms for a paired fold, nearest assignment; approach/contact/close; lift based on measured span; verify each held landmark twice; transfer toward opposite edge; lower/release/retreat; verify visible landmark alignment and extent reduction. Two explicit sleeve folds precede a hem/outline fold if available. |
| stack_blocks (optional) | Same generic stack scaffold with visible object instances | Uses measured surface/visible extent geometry, without the old block oracle or cuboid asset dimensions. Scenes with unrelated visible object instances can be ambiguous. |

Source selection is lexical, not a general language planner. Footprint order and limb pairing are visible-geometry heuristics, not inferred native task answers. All choices and measurements are in debug. Randomized variants use the same geometry and task language with no fixed layout positions. If public instructions imply behavior beyond these scaffolds, a visually completed operation need not be native task completion.

Rigid lift verification compares fresh object displacement since preclose baseline with observed nominal grasp displacement. It requires >20 mm upward object and robot displacement, <28 mm displacement mismatch, and two distinct native-step observations. Cloth verification uses each held keypoint instead of object centroid: >12 mm keypoint rise, >20 mm robot rise and <35 mm mismatch, twice. Gripper closure alone never establishes a grasp. A carry offset is computed only after this check and explicitly remains an approximation of attachment, not a new observed pose.

Press verification measures fresh face displacement along the fixed precontact normal, exceeding max(2.5 mm, estimated depth uncertainty), after the bounded stroke is reached. A color change or gripper position alone is insufficient. No native activation is claimed. This rule may reject correctly activated short-travel buttons or an occluded button. It may also misinterpret surface-estimation drift as motion, pending calibration tests. After verified pressing, the controller retracts before selecting the next number.

Placement verification checks fresh source/destination horizontal separation and visible source-low to destination-top gap, then <12 mm inter-observation source drift in two accepted observations. The vertical gap allowance is [-40,+25] mm to accommodate visible bowl nesting/container entry. This is permissive visible evidence, not proof of support or stability. Fold verification requires each released source landmark within 45 mm of its stored destination and horizontal visible-extent norm reduced below 95% of its prefold value, then stability in two observations. Self-occlusion can prevent that verification even when a native fold succeeds; the controller stops instead of inventing evidence.

**Limits and baseline choice.** This deliberately uses fixed nonnegative proportional amplitudes, explicit dead zones, bounded local history (12 events), and a finite state scaffold. ReliabilityStep is not imported. Its added adaptation is not justified by the small, correlated prior visual sample and would confound whether failures arise from geometry, identity, sign decisions or contact. There is no adaptive confidence pretending to be calibrated. The baseline is suitable for debugging those components separately. Static-goal descent arguments do not apply to cloth, moving conveyors, changing visible surfaces, wrist-camera occlusion or contact. A correctly chosen direction can still miss a moving target, drag cloth incorrectly, or fail to grasp.

Resource controls: at most 180 ask_jev calls; default at most 45 restricted perception calls; a 19-minute elapsed-time check before new step work; 32 observations per phase; two bounded hold/relabel recovery attempts before stopping; three-observation live memory; bounded history; and no internal artifact writes. Settings may optionally override semantic_refresh_steps (clamped 1..10), memory_ttl_steps (1..8), and max_perception_calls (1..100). The required gpu/existing_root/run_dir/seed settings are accepted but unused: callbacks own GPU/transport and output, no existing_root assets are read, and the controller has no random policy sampling. OpenCV RANSAC may use process-global randomness, so bitwise reproducibility still requires runner control. Native ticks are never extended. Callback calls cannot be preempted from this synchronous interface: the supervisor must enforce the 20-minute hard timeout and 800 MB disk limit and bound callback latency. Duplicate native_step inputs return the previous result without another model/perception call; the runner must deduplicate command retransmission. Native step regressions stop.

**Precise untested assumptions and known coverage limits.** Every numbered item below is untested in this worker session, even where a source interface supports the convention.

1. NumPy, SciPy Rotation, and OpenCV LK/RANSAC functions are installed and importable in the runner environment. No syntax/import check has been executed here.
2. The runner imports this directory as a package or places it on sys.path so the sibling helper resolves. Arbitrary spec_from_file_location loading without a package/path setup may not resolve the helper.
3. Camera intrinsics/extrinsics are synchronized with RGB/depth, depth is optical Z rather than ray distance, and the environment origin convention matches the reviewed bridge. Depth/image registration and lens distortion have not been calibrated here.
4. The world Z axis is upward and relevant support surfaces are approximately horizontal. Nonhorizontal pickup surfaces require a different contact scaffold.
5. The provided link6 quaternion and +X gripper bias define the nominal point as specified. Local +X is a suitable approach axis; local Y is a suitable jaw lateral reference. Actual finger geometry, safe pinch height and contact center have not been measured.
6. Gripper state indices and 0=closed/1=open semantics match the supplied interface. The controller logs closure feedback but does not treat a numerical opening as force or object-contact evidence.
7. The executor preserves nominal grasp point when changing orientation, uses world quaternions, enforces action bounds, and handles omitted arms as fixed. Observed IK can fail even when a nominal point appears reachable.
8. The reduced RGB-only perceive payload is supported. The callback returns the specified schema, labels all relevant objects consistently, and does not hallucinate OCR or garment landmarks. The controller cannot independently prove semantic truth.
9. Lexical label/appearance matching is adequate for actual instruction wording. Pronouns, negation, relational referring expressions, unusual synonyms, ordinal sequences and compound instructions are not generally parsed. Unknown instructions can select a single candidate while still failing native intent.
10. Button instructions are explicit enough for sequence parsing. Numeric ordering over visible labels assumes all required buttons are visible. Counts, decimals, negative numbers and complex repeat/reverse instructions are not supported reliably.
11. Buttons move visibly by more than about 3 mm under a <=6 mm nominal stroke. Tool-center contact corresponds to physical fingertip contact. A force-only, capacitive or tiny-travel button may never pass visual verification.
12. Vision polygons isolate target surfaces. A bowl outline encloses cavity/background, and a garment outline may include table pixels; quantile trimming cannot always remove these errors. The 3 mm uncertainty floor is a heuristic and may be optimistic.
13. Multi-camera visible-surface centroids agree within 25 mm, object motion between frames remains under 100 mm, and chromaticity/semantic labels remain stable. Same-colored crossing items and severe occlusion can break identity and lead to a conservative stop or false association.
14. Forward/backward flow checks reject drift often enough. Textureless cloth, reflective bowls, printed button boundaries, moving robot occluders and large wrist motion may force expensive semantic refresh or lose tracks.
15. The bowl upper-depth extrema are physical, graspable rim locations. Thin rims, broad rims, nested bowls, handles, tilted vessels and interior-return depth can defeat this approximation.
16. Visible lower envelopes are useful for placement despite unseen bottoms. Bowl nesting and block stacking may need shape-specific contact geometry beyond the current visible-surface scaffold. The current stack-member exclusion relies on stable IDs through release.
17. Largest visible footprint is an acceptable base when public instructions do not specify order. Occlusion and perspective-induced visible shape changes can bias measured extents. Optional stack_blocks assumes its object category does not include unrelated distractors.
18. A single pickup-and-lift, or one language-specified placement, satisfies general_pickup intent. Repeated pickup of all objects, handovers and specified lift distances are not implemented as separate scaffolds.
19. One matched pickup satisfies conveyor task intent. Multiple required pickups, moving destination placement and multi-object catch scheduling are not implemented. Two-frame linear lead is valid only over short native-step horizons; acceleration and callback/physics timing can invalidate it.
20. Hem-to-shoulder, explicitly requested sleeve folds, or one long-axis half-fold matches the native cloth objective. The controller cannot infer an unstated fold pattern. It has no material model, force estimate, bimanual tension controller or wrinkle-smoothing action.
21. Cloth source and destination landmarks remain visible and consistently named from the selected camera through lift and release. The same corner's pixels may become occluded under a correct fold; the implementation then stops, and may never reach the desired native success rate.
22. Cloth local flow corresponds to material points rather than shadows/background. Fold verification based on extent reduction plus landmark alignment is useful evidence, not a topological or native fold certificate.
23. Two postaction frames are enough to reject accidental lifts or unstable placements. Gripper occlusion, viewpoint-dependent centroid changes, transient settling and external motion can defeat this check. Native evaluator outcomes remain necessary.
24. Clearance offsets, contact tolerances, phase limits and arm choice fit actual reachable workspaces. The nearest-arm heuristic has no kinematic feasibility solver, and the point guard does not certify collision-free arm/hand motion or object clearance.
25. Synchronous callback latency and refresh frequency fit 20 minutes and native action budgets. The 45-call perception cap may be the limiting factor in textureless scenes or lengthy folds/stacks. No token, latency, disk or success measurements have been collected here.
26. Native instruction text stays stable during the episode and native_step advances monotonically on execution. Dynamic stage-specific instructions currently cause a stop. The runner deduplicates retries rather than executing a repeated result twice.
27. The returned Jev choice tokens match negative/hold/positive and the native answers wrapper. Confidence is not used as a calibration signal. Structured-state consistency and effective sign accuracy remain unmeasured for both schemas.
