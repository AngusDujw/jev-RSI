# 额外十个 LIBERO-Plus Goal 任务的 Jev 阶段合同（2026-10-08）

这是在[此前十任务盘点](2026-10-08-ten-task-jev-contracts.md)之外**新增的十项**，没有复用此前的 RoboDojo 五项、奶酪入篮/汤罐入篮及三个黑碗空间任务。任务 ID 与任务族名称逐项对照[官方 LIBERO-Plus `libero_goal` task map](https://raw.githubusercontent.com/sylvestf/LIBERO-plus/main/libero/libero/benchmark/libero_suite_task_map.py) 的索引 1098、1144、1163、1202、1252、1296、1335、1383、1423、1458；对应的是指定 `language_1/view_0_0_100_0_0/initstate_0` 的变体，不应把不同语言/视角/初态版本合并成绩。

本轮交付的是**任务处理与模型输入候选**。当前[十任务合同模块](../code/scripts/libero_ten_task_workflows.py)定义 10 个公开任务和四种动作原语，共 121 个阶段实例；[采集入口](../code/scripts/run_libero_ten_task_capture.py)只预留账本并采集双视角 RGB-D/标定/本体状态，**不调用 Jev 或 GPT-6、不执行任务动作**。因此以下十项目前都是待离线核查和物理验证的候选，成功回合数为零；不能把“有阶段表”写成“Jev 已能推进十任务”。

## 共用模型输入与推进条件

每次决策的 `state` 由公开语言、当前阶段合同、可见实体证据、当前 TCP/夹爪、本阶段目标、目标减当前的毫米误差、姿态误差、近三次真实执行反馈、阶段证据和来源组成。来源只允许双视角 RGB-D、相机标定、机器人本体/自身 mesh 与已执行动作历史。任务 ID 供运行器选任务，不代替公开语言或目标观测；BDDL、物体真值、奖励、官方成功标志只可进入离线评估，绝不进 Jev 输入。

Jev 的独立选择题是 XYZ 的 `negative/hold/positive`、需要时 RX/RY/RZ 的方向、夹爪 `open/close/keep`、阶段 `continue_phase/advance/stop`。当前合同模块仅在本阶段对应的**当前可观测 gate 为 true** 时提供 `advance` 选项；`false/unknown` 时保留当前阶段或停止，不把待检查状态当失败。它**还没有** `reobserve/retry` 入口、视觉目标生成、动作幅度/执行器接线和真实回合控制。未来接入时必须保留 Jev 对动作和阶段边的最终选择，并逐帧记录拒绝的非法 `advance`；不能用模块预先算出的误差符号代替模型方向。

尤其应把 `TaskPlan` 中的源、接收器、关系词作为**公开语言槽位**，再与当前可见检测逐项关联；不能仅把硬编码英文改写当作仿真器本回合的真实公开指令。当前 `decision_request` 尚只送 `plan.language`、阶段合同和外部提供的数值目标，源/接收器关系槽位没有单独出现在 `state`；这在接入前必须补齐和核对。多步骤任务换原语时需要新观察，不能沿用上一阶段的旧目标。

## 十项任务合同

共同的 `pick_place` 原语为 `observe → select_grasp → approach → align → descend → grasp → test_lift → lift → carry → lower → release → retreat → verify`。闭爪不等于持有，短抬可见共运动证据为独立阶段；释放后的关系只能用新观察核验。下表列出不同于共用抓放的处理与 Jev 应看到的特有事实。表中的 gate 是可见/本体代理，不是隐藏任务成功谓词。

| # | `libero_goal` ID / 新任务 | 候选原语与阶段重点 | Jev 输入的任务专属可观测事实；禁止的捷径 |
|---:|---|---|---|
| 1 | `1098` 打开柜子中层抽屉 | `open_drawer`：`observe → approach → align → contact → grasp → pull → release → verify` | 用图像确认**中层**把手、柜面法向、把手位移和抽屉开口前后差。不能凭“拉”指令或隐藏 `Open` 谓词推进到完成。 |
| 2 | `1144` 将碗放在炉面 | `pick_place`；放置目标是可见炉面上可用支撑区 | 碗沿/可抓边、炉面可见支撑多边形、夹指与炉体的碰撞余量、碗抬升共运动、释放后的相对支撑关系。不能把炉体中心当精确放置坐标。 |
| 3 | `1163` 将酒瓶放到柜顶 | `pick_place`；抓取和放置需保留瓶身朝向与高度 | 可见瓶颈/瓶身边界、指垫重叠、柜顶边缘及上方净空、瓶身随抬升/释放后的姿态。不能由细长物体的局部顶面估计整瓶高度。 |
| 4 | `1202` 打开上层抽屉并把碗放入 | `open_drawer` 8 阶段 **再接** `pick_place` 13 阶段，共 21 阶段 | 必须先观察**上层**把手及打开后的抽屉内部，再重新选碗与内部放置区；若抽屉未可见打开，不能跳到碗放入。两个原语之间重观测，目标和夹爪状态重新校验。 |
| 5 | `1252` 将碗放到柜顶 | `pick_place`；与 #2 共用抓放，只替换接收器几何 | 柜顶可见平面、碗沿高度、桌面到柜顶的净空和放置稳定性；柜门/侧壁不是柜顶。 |
| 6 | `1296` 将盘子推到炉子前方 | `push`：`observe → approach_rear → lower → push → retreat → verify` | 可见盘子、炉子前缘和空走廊；闭爪可作为推具但不是抓取；每块动作比较盘子与 TCP 的实动。目标“炉前”是可见关系，不能偷读目标区域谓词。 |
| 7 | `1335` 将奶油奶酪放进碗里 | `pick_place`；低矮物体先用可见表面/指垫接触候选 | 奶酪可见厚度、桌面净空、闭爪前真实下降、短抬共运动、碗口而非外壁。不能把此前“奶酪入篮”的成功率迁移成这项结果。 |
| 8 | `1383` 打开炉灶控制 | `turn_control`：`observe → approach → align → contact → grasp → turn → release → verify` | 控制钮身份、可见中心/切向方向、机器人实际旋转或拨动、前后可见指示变化。没有可见变化就保持未验证，不能把隐藏点火状态送模型。 |
| 9 | `1423` 将碗放到盘子上 | `pick_place`；源与盘子需重新由当前视图确认 | 碗沿、盘面边界、释放后新观察的上下关系；它与此前 `libero_spatial:1282` 不同任务/变体，旧 2/2 不迁移为本项成绩。 |
| 10 | `1458` 将酒瓶放入架子 | `pick_place`；接收器是可见酒架开口/支撑，不是简单水平桌面 | 瓶身朝向与夹爪包络、架口位置/深度、带持物体的通道净空、释放后瓶身是否仍可见处于架内；不可把架体外表面当入口。 |

## 离线核查与下一步

已用官方 task map 在内存中核对 10 个 ID，全部落在 `libero_goal` 且对应上表的任务族；这只验证任务索引和基本语义，不验证可见目标几何。现有 Python 合同模块在不调用模型/仿真的条件下，对 10 项共 121 个阶段分别生成可 JSON 序列化的请求，`gate=true` 时均包含 `advance`；这仅是**静态接口检查**。没有进行物理回合或新增实验成功率。

下一项有意义的工作是先采集每项一个未见初态的公开 RGB-D，离线核查实体身份、阶段目标能否由观测构造和 gate 是否可测；随后选不同原语各一项做有界闭环开发。若三次连续崩溃、单次预计超过 2 小时 GPU 或 5 GB 写盘，按协议升级，不为凑满十项继续跑。现有共同动作函数 $Q$ 应在各阶段使用相同参数化输入（目标误差、测量不确定度、命令/实动反馈和限幅），不能按任务名分别拟合十套 gain；抽屉、推盘、旋钮等阶段须单列非静态或接触任务的适用边界。

`jev-control-formulation` 的 CIRCLE-1 收敛到固定输入合同与一套 $Q$ 的新状态对照；`libero-generic-vision` 的 CIRCLE-1 先以这十项的单帧可见性审计判断哪些身份/接收器根本无法由当前视觉稳定提取，避免重复修改提示词并把失败写成新成绩。
