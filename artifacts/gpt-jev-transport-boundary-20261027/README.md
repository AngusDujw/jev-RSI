# 约15分钟生成断流：受控检查结果

## 结论

确实复现了模型响应流在代码输出中途被截断；不是原实验的SSH隧道、机器人或两路并发才会发生，也不是本地代码写死900秒总读流时间。当前证据更指向模型长响应路径的服务端或中间网关中断，但不能命名具体关闭连接的一层，也不能声称存在已确认的官方900秒模型限制。

## 生成本身的成本

HTTP2成功例的用量为8517输入、17299输出，其中9840推理tokens。首次方法参数在537.620秒，之后约179.723秒至完整返回。这是一份完整224行程序及接口/协议，不是几条高层步骤。它证实生成本身存在较大的输出前工作量，但不能把全部输出前时间等同于内部GPU计算，也不能据一例量化提示词/xhigh/协议的因果影响。

HTTP1失败尝试用量未知，不计为零；本轮2次推理共1已知+1未知。生成的方法只做四字段/ASCII/静态源检查，未执行，不能作为新的LIBERO成功案例。

## 还有什么没确定

- 截断发生于服务端、远端代理节点还是其他中间层，客户端没有对应服务日志或抓包证据以逐跳定位。
- 代理历史warning日志有网络错误，但不能按源端口对应到此前失败流，因此不能归因。
- HTTP1未见合法终止块说明本次响应不完整，不是服务端明确返回某个超时错误码。
- HTTP2成功的生成更早进入代码输出，且未跨900秒；随机生成长度、负载和协议变量未隔离。
- 本地直连不能建立连接，暂时没有可用的无代理长流对照。本次没有切换或修改全局代理。
- [OpenAI配置说明](https://learn.chatgpt.com/docs/config-file/config-reference)中的CLI流超时不是这段独立Python桥接器的配置入口；本轮依据实际读流代码和测试结果判断。

## 下一步边界

只增加本地timeout不能保证完整交付：本次2100秒预算仍在902秒被提前终止。后续应先验证长流交付和保留进度的恢复机制，再测机器人泛化。不能将本次HTTP2的单次交付直接宣布为修复，也不应继续把此前的0Jev生成失败称作物理策略失败。
