Use the previously selected official GPT top-five RoboDojo tasks: general_pickup, fold_clothes, press_by_number, match_and_pick_from_conveyor, stack_bowls. Preserve the released simulator's initial seed 0 and reset seed equal to the selected layout ID; record these separately. Keep failures and service failures explicitly recorded. No scene alteration, task-specific rescue controller, demonstrations, or task-ground-truth input is added. Native evaluator outputs are scoring-only.

Conditions are pure GPT (replan every 5 actions), GPT plus Jev reuse, fixed mean reuse interval, and fixed maximum reuse interval. GPT predicts 20 actions in every condition. The paper gate may approve one extra 5-action segment, so a single GPT proposal executes at most 10 actions. Preserve the released tracking and IK guards in all conditions.

For each task, terminate all four attempts in pure and Jev conditions (40 calibration attempts in total). Then derive that task's mean and maximum actually executed actions per GPT proposal from all four Jev attempts, including native-terminal and controller-interrupted chunks. For an unscored simulator/service interruption or a policy-error result, exclude only the final right-censored interval: subsequent completed GPT requests close earlier intervals, but an infrastructure stop does not define a policy's intended last interval. Do not replace such attempts or invent a native score. Record scored/usable attempts and censored-tail counts. Require at least one measurable interval per task. Round the mean to the nearest integer with half-up rounding and a minimum of one; cap both intervals at 20, the prediction horizon. Freeze each task’s values before its eight fixed-interval attempts (40 fixed attempts in total). Report observed and full nonterminal interval distributions to expose truncation effects. The working interpretation of "mean/max steps" is the number of robot actions between GPT requests, as stated to the user; a later user clarification takes precedence before the fixed-interval phase.

An interval is the robot-step difference from one completed GPT request to the next, with the last interval ending at episode termination. Zero-step correction requests therefore remain in the interval denominator; local safety-hold steps also remain in the physical-step count. Accepted tool-result intervals are reported separately. No extra calls or failed trials are silently removed.

The mean/max schedules are fitted on the same four Jev layouts and are development-set ablations. Report per-episode total robot steps as well as per-GPT intervals. Infrastructure interruptions remain explicit; their partial steps are not silently averaged into a complete-episode performance claim.

To use freed GPUs during the Jev tail, a task may freeze its own values once all four of its Jev attempts have terminated; it does not use any other task's data. Frozen entries are immutable and protected by a file lock. Task-filtered fixed jobs may then overlap still-running Jev jobs on disjoint, verified-free GPU slots within the same four-card limit. No fixed job starts for a task with missing Jev attempts. Global summaries use unique staging files so concurrent task groups cannot collide; raw completed-case ledgers remain authoritative, and a final summary is regenerated after all groups finish. This changes scheduling only, not calibration samples, prompts, action guards or budgets.

All parallel pools retain global `--slots-per-gpu 2` so simulator ports and Kit roots use the same namespace. `--worker-slots` selects only free slots within that capacity. Fixed pools use `--skip-existing`: an atomic directory claim gives each task/layout/condition exactly one owner, and another pool leaves an already claimed case untouched. The pure/Jev paths retain their strict unfinished-case guard. The coordinator reserves live pools' slots, checks GPU memory, and verifies all forty fixed cases have finished before producing the final report.

Use the local signed-in ChatGPT Pro account for GPT transport, never an OpenAI Platform API key. ## Reproduction limits

The paper reports Jev results only for Align Blocks and General Pickup on development layouts 0–4. Applying the gate to the other selected tasks and using layouts 0–3 is a user-requested extension. The original gate prompt, threshold and full implementation are not published. A local Pro transport also differs from the release's API provider; any differences in model identity, prompt transport or usage counters must remain explicit. No success or speedup is claimed before actual execution.

All four conditions use the Jev subsection's zero-shot B25 regime. This is not a reproduction of the main table's one-shot J12/B12 Memory-task setting. In particular, the historical task-selection scores are not matched-setting reference scores for this batch. The five-task comparison measures the reconstructed gate under a common regime; it cannot establish equivalence to the complete main-table protocol.

The native ChatGPT Pro backend accepted an actual `gpt-6-astra` / `xhigh` function-call probe. A complete released-harness payload was rejected with HTTP 400 because `prompt_cache_options` is not supported on this model. The bridge therefore removes only provider cache hints (`prompt_cache_options` and nested `prompt_cache_breakpoint`), without flattening or deleting model-visible messages, images or tool definitions. Cache-efficiency equivalence to the paper is not asserted.

The released GPT prompt explicitly promises execution of at most `execute_horizon` actions. In the Jev condition only, its execution upper bound is changed from five to ten, while the first dispatch remains five and the prediction remains twenty. Pure GPT and fixed schedules retain their configured execution bound. The actual tool receipt covers all actions truly executed, including an approved suffix. This necessary scheduling-contract difference is an additional reconstruction choice; results compare complete policy conditions and cannot isolate Jev reasoning independently of the execution-bound wording.

The released consecutive-error tracking guard is preserved across the internal 5+5 boundary of one proposal through a lightweight execution-context RPC. A new GPT proposal resets the guard as before. A prefix already stopped by the released tracking rule cannot be extended by Jev. Otherwise splitting a ten-action proposal into two dispatches would reset the error streak and weaken the guard. The Jev input also states the released gripper semantics: reported values are previous normalized commands, not sensed aperture or grasp evidence.
